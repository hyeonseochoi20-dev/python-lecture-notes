이 챕터에서 처음 만나는 용어들

💡 미리 알아두면 훨씬 편한 기본 용어
용어쉬운 설명
인터프리터 (Interpreter)사람이 쓴 파이썬 코드(.py 파일)를 한 줄씩 읽어서 컴퓨터가 이해할 수 있는 명령으로 바꿔 즉시 실행해주는 프로그램. "Python을 설치한다"는 것은 사실 이 인터프리터 프로그램을 내 컴퓨터에 설치한다는 뜻입니다.
터미널 / 명령 프롬프트마우스로 아이콘을 클릭하는 대신, 글자로 된 명령어를 입력해서 컴퓨터에게 작업을 시키는 화면. Windows에서는 "명령 프롬프트(cmd)"나 "PowerShell", macOS/Linux에서는 "터미널(Terminal)"이라고 부릅니다.
패키지 (Package) / 라이브러리 (Library)다른 사람이 미리 만들어 둔, 재사용 가능한 코드 묶음. 예를 들어 requests는 "인터넷에서 데이터를 가져오는 기능"을 이미 다 만들어 둔 패키지입니다. 내가 직접 그 복잡한 기능을 처음부터 만들 필요 없이 pip install requests 한 줄로 가져다 쓸 수 있습니다.
PATH (환경변수)운영체제가 "명령어를 입력받았을 때 실행 파일을 어디서 찾아야 하는지" 알고 있는 폴더 경로들의 목록. python이라고만 쳤을 때 실제 python.exe 파일이 어디 있는지 컴퓨터가 알려면, 그 파일이 있는 폴더가 이 PATH 목록에 등록되어 있어야 합니다.
IDE / 에디터코드를 작성하고, 실행하고, 오류를 확인하는 프로그램. 이 강의에서는 VS Code(Visual Studio Code)를 사용합니다. 메모장과 다르게 문법 강조, 자동완성, 오류 표시 등을 지원합니다.
가상환경 (Virtual Environment)프로젝트마다 독립된 "미니 파이썬 설치본"을 만들어서, 프로젝트별로 패키지 버전을 따로 관리하는 기술. 아래에서 왜 필요한지 아주 자세히 다룹니다.

Python 설치 가이드

Windows 설치 절차

  1. 공식 웹사이트 방문: python.org에서 최신 버전 다운로드
  2. 설치 파일 실행: python-3.xx.x-amd64.exe 파일 실행
  3. 필수 옵션 선택:
    • ☑️ Add Python to PATH (매우 중요!)
    • ☑️ Install launcher for all users
    • ☑️ Add Python to environment variables
  4. 설치 확인: 
    # 명령 프롬프트 또는 PowerShell에서
python --version
# 예: Python 3.12.0

pip --version
# 예: pip 23.3.1 from ... (python 3.12)
💡 "Add Python to PATH"를 왜 반드시 체크해야 할까?
앞서 설명했듯 PATH는 "명령어를 실행할 때 파일을 찾아볼 폴더 목록"입니다. 이 옵션을 체크하지 않으면, Python 인터프리터(python.exe)는 컴퓨터 어딘가에 분명히 설치되었지만, 그 위치가 PATH 목록에 등록되지 않습니다. 그러면 터미널에 python이라고 입력했을 때 운영체제가 "그런 명령어를 어디서 찾아야 할지 모르겠다"며 다음과 같은 오류를 보여줍니다. 
'python'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는
배치 파일이 아닙니다.
이 오류가 뜬다면 대부분 설치 시 PATH 체크박스를 놓친 경우입니다. 해결 방법은 두 가지입니다: (1) Python을 제거 후 재설치하면서 이번엔 체크박스를 꼭 체크하거나, (2) 제어판 → 시스템 → 고급 시스템 설정 → 환경 변수에서 Python 설치 폴더 경로를 직접 PATH에 추가합니다. 대부분의 입문자에게는 재설치가 훨씬 간단하고 안전합니다.

macOS/Linux 설치

  • macOS: 기본적으로 Python이 설치되어 있을 수 있으나, brew install python으로 최신 버전 설치 권장
  • Linux: sudo apt update && sudo apt install python3 python3-pip (Ubuntu/Debian 기준)
  • 버전 확인: python3 --version

가상환경 (Virtual Environment) 완전 정복

왜 가상환경이 필요할까? (의존성 지옥 이야기)

처음 파이썬을 배울 때는 "그냥 pip install로 필요한 거 설치하면 되지 않나?"라고 생각하기 쉽습니다. 하지만 실제로 여러 프로젝트를 진행하다 보면 반드시 마주치는 문제가 있습니다. 아래 시나리오를 따라가 봅시다.

💡 가상환경 없이 작업하면 벌어지는 일 (Dependency Hell, 의존성 지옥)
1. 6개월 전에 만든 프로젝트 A는 requests 라이브러리의 2.25 버전 기능에 맞춰 코드를 작성했습니다.
2. 오늘 새로 시작하는 프로젝트 B는 최신 기능이 필요해서 requests의 2.31 버전을 설치해야 합니다.
3. 가상환경 없이 pip install requests==2.31을 실행하면, 컴퓨터 전체에 단 하나만 존재하는 전역(global) Python 환경의 requests가 2.31로 덮어써집니다.
4. 그 순간, 예전에 잘 돌아가던 프로젝트 A가 갑자기 오류를 내며 멈춥니다. 버전이 바뀌면서 프로젝트 A가 의존하던 옛날 방식의 함수가 사라졌거나 동작이 달라졌기 때문입니다.

이렇게 "한 프로젝트를 위해 패키지 버전을 바꾸면 다른 프로젝트가 고장 나는" 상황을 의존성 지옥(Dependency Hell)이라고 부릅니다. 가상환경은 이 문제를 프로젝트마다 서로 완전히 분리된 패키지 설치 공간을 만들어줌으로써 근본적으로 해결합니다.

가상환경(venv)은 실제로 무엇을 하는가?

python -m venv myproject를 실행하면, myproject라는 이름의 폴더 안에 그 프로젝트만을 위한 완전히 독립된 파이썬 실행 환경 한 벌이 통째로 복사됩니다. 이 폴더 안에는 다음이 들어있습니다.

  • 독립된 python.exe (또는 python 실행파일): 원본 파이썬을 가리키는 복사본/링크
  • 독립된 site-packages 폴더: pip install로 설치한 패키지들이 저장되는, 이 프로젝트만의 전용 창고. 다른 가상환경이나 전역 환경의 site-packages와는 완전히 분리되어 있어 서로 영향을 주지 않습니다.
  • 독립된 pip: 이 가상환경 전용 패키지 설치 도구

"활성화(activate)"는 정확히 무슨 일을 할까?

💡 activate의 원리
가상환경을 만들기만 하고 활성화하지 않으면 터미널은 여전히 컴퓨터 전역에 설치된 파이썬을 사용합니다. source myproject/bin/activate (또는 Windows의 myproject\Scripts\activate)를 실행하면, 터미널은 앞서 배운 PATH(환경변수)의 맨 앞자리에 이 가상환경의 실행파일 폴더 경로를 임시로 끼워 넣습니다. 그 결과 터미널에 python이나 pip를 입력했을 때, 운영체제는 PATH 목록을 순서대로 뒤지다가 가상환경 폴더를 전역 설치본보다 먼저 발견하게 되어, 자연스럽게 가상환경 쪽 파이썬과 패키지들이 사용됩니다.

활성화되면 터미널 프롬프트 맨 앞에 (myproject)처럼 가상환경 이름이 괄호로 표시되는데, 이것이 "지금부터 이 터미널에서 실행하는 모든 python/pip 명령은 전역이 아니라 이 가상환경 안에서 일어난다"는 시각적인 신호입니다.

deactivate를 실행하면 PATH에 임시로 끼워 넣었던 경로가 제거되고, 다시 원래의 전역 환경으로 돌아갑니다.

가상환경 생성 및 관리 명령어 모음

# 가상환경 생성
python -m venv myproject
# 또는 Python 3.3 이상에서
pyvenv myproject

# 가상환경 활성화
# Windows:
myproject\Scripts\activate

# macOS / Linux:
source myproject/bin/activate

# 활성화 확인 (프롬프트가 (myproject)로 변경됨)
(myproject) $

# 패키지 설치
pip install requests flask numpy pandas

# 설치된 패키지 확인
pip list
pip freeze > requirements.txt  # 배포용 파일 생성

# 가상환경 비활성화
deactivate

# 가상환경 완전 삭제 (폴더 삭제)
rm -rf myproject  # 또는 디렉터리 직접 삭제

requirements.txt는 왜 필요할까?

💡 재현 가능성(Reproducibility)
pip freeze > requirements.txt를 실행하면, 현재 가상환경에 설치된 모든 패키지와 그 정확한 버전 번호가 텍스트 파일 하나에 기록됩니다 (예: requests==2.31.0). 이 파일을 동료에게 공유하거나 Git 저장소에 올려두면, 동료는 자신의 컴퓨터에서 pip install -r requirements.txt 한 줄만으로 나와 정확히 똑같은 버전의 패키지 조합을 그대로 재현할 수 있습니다. "내 컴퓨터에서는 되는데 왜 네 컴퓨터에서는 안 되지?" 같은 문제를 크게 줄여주는 핵심 파일입니다.

.gitignore에는 왜 .venv를 반드시 포함해야 할까?

💡 가상환경 폴더는 Git으로 관리하지 않는 이유
1. 용량 문제: 가상환경 폴더 안에는 설치된 모든 패키지의 실제 코드가 통째로 복사되어 있어 수백 MB에 달할 수 있습니다.
2. 플랫폼 종속성: 가상환경 안의 실행파일은 그것을 만든 운영체제(Windows/macOS/Linux)에 맞춰져 있어서, 다른 운영체제에서는 그대로 작동하지 않습니다.
3. 재현 가능한 대안이 이미 있음: 위에서 만든 requirements.txt 파일 하나면 어떤 컴퓨터에서든 필요한 패키지를 다시 설치할 수 있으므로, 무거운 가상환경 폴더 자체를 통째로 공유할 필요가 없습니다.

그래서 가상환경 폴더(.venv)는 .gitignore 파일에 등록해서 Git 저장소에 아예 올라가지 않도록 하고, 그 대신 requirements.txt만 커밋하는 것이 표준적인 관행입니다.

가상환경 활용 실전 예제

프로젝트 구조 예시

my-python-project/
├── .venv/                  # 가상환경 폴더 (Git에 포함 안 함)
├── src/                    # 소스 코드
│   ├── main.py
│   └── utils/
├── tests/                  # 테스트 코드
├── requirements.txt        # 필수 패키지 목록
├── README.md
└── .gitignore
폴더/파일역할
.venv/이 프로젝트 전용 가상환경. 위에서 설명했듯 Git에는 올리지 않음
src/실제로 동작하는 파이썬 소스 코드. utils/처럼 기능별 하위 폴더로 나눠 정리
tests/코드가 의도대로 동작하는지 검증하는 테스트 코드 모음
requirements.txt이 프로젝트가 필요로 하는 패키지와 버전 목록 (재현 가능성 확보)
README.md프로젝트 설명서. 무엇을 하는 프로젝트인지, 어떻게 실행하는지 적어둠
.gitignoreGit이 추적하지 않을 파일/폴더 목록 (.venv/, __pycache__/ 등)

실전 워크플로우

  1. 프로젝트 폴더 생성: mkdir myproject && cd myproject
  2. 가상환경 생성: python -m venv .venv
  3. 가상환경 활성화: source .venv/bin/activate (Linux/macOS) 또는 .venv\Scripts\activate (Windows)
  4. 필수 패키지 설치: pip install -r requirements.txt
  5. 개발 진행: python src/main.py
  6. 작업 완료 후: deactivate
